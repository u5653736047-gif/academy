## 1. 测试分层

| 层 | 测什么 | 怎么测 | 是否需要真模型 | 阶段 |
|---|---|---|---|---|
| **L1 单元** | 纯逻辑：规则匹配、路径归一化、命令解析、判定结果 | 参数化测试，输入输出表 | 否 | **一** |
| **L2 集成** | agent 循环 + 工具 + 闸 | 假模型（stub provider）+ 真工具 | **否（关键）** | **一** |
| **L3 端到端** | Electron 应用整体：对话、弹窗、中止 | 自动化 UI 驱动 | 视情况 | **一** |
| **L4 人工验收** | 需求第 5 节的三个成功指标（试点） | 真人使用 | 是 | **二** |

**L2 是重点**：agent 类项目的测试难点在于"模型不确定"。解决办法是把模型换成**可编排的假供应商**——给定输入，返回预设的 toolCall 序列。这样"模型说要删库 → 闸拦截 → 模型收到拒绝原因"这条链路可以完全确定性地测。

【待填】假模型怎么接（pi 的 provider 接口 / `setDefaultStreamFn`）

> 📌 **阶段一的测试策略就是 L1–L3。** 阶段一没有试点、没有真实学生，L4 无从谈起。
> 阶段一靠"用例表全绿 + 集成链路确定性可测 + 端到端能驱动"来证明它成了，另加 02-scope 里的 A1–A5。

## 2. L1：单元测试【阶段一】

重点对象：
- 权限规则匹配（用例表 [permission-cases.md](./permission-cases.md) 的 A/B/C/D 组）
- **shell 命令解析**（C 组全部用例。这块是最大风险，覆盖率要拉满）
- 路径归一化与边界判定（含符号链接、`..`、Windows 盘符）

## 3. L2：集成测试【阶段一】

- 会话创建 → 提问 → 工具调用 → 闸拦截 → 用户决策 → 继续
- 子代理委派全流程（含"子代理的动作走同一道闸"这条断言）
- **闸加载失败的启动自检**（扩展加载失败是静默的，必须自己检查）
- 会话 JSONL 重建（重启后恢复上下文）

## 4. L3：端到端【阶段一】

【待填】用什么驱动 Electron（Playwright / Spectron 替代品）

重点场景：
- 审批弹窗的三个来源形态（主 agent / 子代理 / 灰区判官）
- 超时 = 拒绝
- 中止主 agent / 中止指定子代理

## 5. L4：人工验收【阶段二】

> ⚠️ **本节整节属阶段二。** 阶段一没有服务端、没有学生群体，试点无从谈起。
> 阶段一的验收标准见 [../02-scope-v1.md](../02-scope-v1.md) 第二节末（A1–A5）。

对应需求第 5 节，试点看三件事：

1. 每周活跃人数
2. 反馈里"解决了问题"占比
3. 周留存

**另外必须做一项**（不是需求里的，是我们自己加的）：**出处抽查**——拿 20 道真题跑一轮，人工核对引用是否真实存在于资料中。试点前必须做，不能只靠提示词约束。
