## 决定 1：权限闸挂在哪一层？

### 问题是什么

agent 每次要执行工具（读文件、跑命令、改代码）之前，我们的闸要拦下来判定。问题是：**这个"拦"的代码，挂在哪个位置？**

### 三个选项

| | 做法（大白话） | 好处 | 代价 |
|---|---|---|---|
| **A** | 挂在 pi 的**扩展**上（生态标准做法） | 可以直接用现成的第三方闸，少写代码 | 这条链上的参数**可以被改动，而且改完不重新检查**——不是真正的安全边界 |
| **B** | 挂在 pi 的**底层钩子**上（我最早提的） | 看到的是模型给的原始参数，改不了 | 要包装官方已经装好的钩子（依赖内部实现）；**用不了现成第三方闸** |
| **C** | **直接把 pi 内置的工具换成我们自己的** | 上面那个"参数能被改"的问题**从根上消失**；有 OpenClaw（一个成熟产品）的现成先例；pi 已导出工具工厂，我们是"包一层"不是"重写" | 要自己组装全部工具；同样**用不了现成第三方闸** |

### 我的推荐

**C**。理由：
1. 它把安全问题从"靠约定"变成"靠结构"——工具是我们自己的，参数进到工具里就是最终值
2. 成本比看起来低：pi 导出了 `createReadTool` / `createBashTool` 等工厂，官方 `sandbox` 示例就是这么覆盖 bash 的
3. 这不是我的发明——OpenClaw 用同一份 pi SDK 做产品，就是这么干的（`builtInTools: []` + 自己的工具）

**如果你更看重"少写代码"而不是"闸真的拦得住"，那就选 A。** 这是个真实的取舍，不是对错。

## 决定 2：自研，还是复用现成的？

### 问题是什么

调研发现 npm 上有 **200 多个** pi 子代理包、几十个权限闸包。要不要直接拿一个用？

### 关键事实（这条决定了上面那个决定）

> **生态里所有第三方权限包都挂在扩展层（选项 A）上——因为它们都是扩展，没得选。**

所以：**决定 1 和决定 2 是同一个决定的两面，必须一起拍。**

| 如果你想要 | 那就只能 |
|---|---|
| 用现成的 `@gotgenes/pi-permission-system`（覆盖我们 7 条需求里的 6 条） | **选 A**，把闸交给它 |
| 更彻底的方案（B 或 C） | **自研，放弃那些包** |

### 我的推荐

**自研（选 C）+ 把 gotgenes 当规格书读。**

三条理由，按重要性排序：

1. **权限闸是唯一一个"它错了就等于没有"的组件。** pi 的官方文档自己写着：*"Extensions run with your full system permissions and can execute arbitrary code"*——扩展和 pi 同进程同权限。把一道闸交给第三方未审计的代码，等于把门锁的钥匙交给别人配。
2. **"覆盖 6/7" 不等于省事。** 缺的那一条（三档用户界面 + Electron 集成）本来就是我们自己的活，所以"零工作量"这个诱惑是不存在的。
3. **这项目本身就是走一遍开发流程的练习。** 权限闸是整个项目里最值得自己写的那块——它是核心复杂度所在。

**代价**：命令解析要自己上 `tree-sitter-bash`；"子会话注册 + 闸共享"的协议要自己实现。
**缓解**：生态里有现成的设计可以抄（见下），不是从零开始。

### 可以抄的现成设计（不用白不用）

| 抄什么 | 从哪抄 |
|---|---|
| 三态返回值命名 `allow / ask / deny` | Claude Code（已被完整固化进发行物） |
| 白名单**不得把通配符放在子命令前**（否则 `Bash(git *)` 能执行任意命令） | Claude Code 的规则校验器原文 |
| 按**能力类别**匹配（读 / 写 / 执行），不按工具名 | Claude Code（`Write`/`MultiEdit` 的规则根本不生效，只有 `Edit` 有效） |
| 风险分两个维度：**破坏性** × **开放世界**（联网/外部副作用） | Codex |
| 档位记忆三级：**本次 / 本会话 / 永久** | Codex 的审批对话框 |
| 白名单锚定到**解析后的可执行路径**，不是命令字符串 | OpenClaw（防 `PATH` 劫持） |
| 「只允许 stdin 的窄白名单」模式（`jq`/`head`/`wc` 这类） | OpenClaw 的 `safeBins` |
| 配置合并**取更严者**；项目内配置**不得放宽权限** | OpenClaw |
| **硬拦截不弹窗**、拦截后让 agent 继续 | Cline |
| 「配置冲突时降级到更安全的一侧 + 明确报错」，不静默采用危险配置 | Codex |
| 三层工具锁：构造时白名单 + 注册表闸 + 运行时重收窄 | `@tintinweb/pi-subagents` |
| 子会话注册协议（先注册进审批服务，再绑扩展） | `@gotgenes/pi-subagents` |

### ⚠️ 绝不能抄的一处

Claude Code 对**非法配置规则**的处理是"跳过那一条，继续运行"。**用户会以为黑名单生效了，其实没有。**

→ **我们必须反向实现：配置里出现非法规则 = 拒绝启动，或整体降级为"全部需要审批"，并在界面上明确报错。**

## 决定 3：子代理怎么跑？

这条调研已经把答案逼出来了，**基本可以直接拍**。

### 推荐：混合路线

| 什么任务 | 放哪 | 为什么 |
|---|---|---|
| 前台、短任务（查资料、看代码） | **主进程内**（独立会话） | 闸天然共享，启动零成本 |
| 后台、长任务、不受信任务 | **独立的 runner 进程** | 跑飞了拖不垮主应用，**可以真杀** |

**依据**：下载量第一的 pi 子代理包（月下载 42.8 万）就是这么分工的。

**这解决了我们之前担心的问题**："进程内跑飞了杀不掉"——因为长任务根本不放在进程内。

### 顺带三个必须记住的实现约束

1. **每个会话一个独立的 `ResourceLoader`**，但**共享一个 `ModelRuntime`**（不然两个会话的扩展会串线）
2. **闸的状态不能放在扩展的模块顶层**（会被所有会话共享）
3. **子代理不会自动继承父的闸**——必须显式实现"子会话注册"，顺序是**先注册、再绑定扩展**

### ⚠️ 一个必须堵的洞

有人的 README 里诚实写了：子代理只要用 bash 跑一句 `pi -p "..."`，就起了一个**全新的、没有任何闸的进程**。

→ 这条要写进权限用例表，把"通过 bash 启动 agent 进程"列为需要拦截的行为。

## 决定 4：第一版范围砍到哪里？

### 问题是什么

需求文档写的是"一个班的学生"，但**现在实际的用户只有你自己**。

### 只服务自己时可以砍的

| # | 能力 | 说明 |
|---|---|---|
| 1 | Electron 安装包 | 直接跑开发模式就行 |
| 2 | 邀请码激活 + 姓名学号登记 | 没有第二个学生 |
| 3 | 服务端"接入服务" | 同上 |
| 4 | 记录上报的"学生可查可关" | 自己看日志文件 |
| 5 | 首次使用告知同意 | 文案给谁看 |
| 6 | **服务端本身** | 资料放本地目录，检索先走本地；通道形状不变，只换实现层 |
| 7 | 课程知识库管理界面 | 自己放文件 |

### **不可砍**的

**权限闸、审计日志、检索子代理的上下文防火墙。**

→ 前两个的价值就是"你自己不会被 agent 搞坏东西"；第三个是多智能体的真正理由。
