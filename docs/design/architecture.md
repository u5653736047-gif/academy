## 0. 阶段划分对架构的影响（先读这一节）

**阶段一只有本地端。没有服务端、没有检索、没有出网。**

```
        ┌─────────────── 阶段一 ───────────────┐   ┌──── 阶段二 ────┐
        │  Electron 应用（学生电脑）            │   │   服务端        │
        │  GUI  +  pi 内核  +  权限闸  +  子代理 │◀─▶│ 知识库/检索/记录 │
        └──────────────────────────────────────┘   └────────────────┘
```

| 架构层 | 阶段一 | 阶段二 |
|---|---|---|
| GUI 四视图 | 对话视图、会话中心、权限中心、设置（去掉激活） | 加激活向导、出处卡片、反馈 |
| Agent 宿主 | ✅ 全部 | — |
| 子代理 | ✅ 通用基座 | 加**资料检索子代理** |
| 权限闸 | ✅ 全部 | — |
| 工具集 | pi 自带（读 / 写 / 执行命令） | 加**课程资料检索工具** |
| 服务端客户端 | **不存在** | ✅ |
| 服务端 | **不存在** | ✅ |

**为什么先切这一刀**：阶段一交付的是**通用骨架**（内核改造 + 人机界面 + 安全闸），阶段二是往骨架里填**课程内容**。骨架立不住就填内容，等于在流沙上砌墙。

> ⚠️ **阶段一的已知局限**：多智能体最硬的那条理由是"检索结果太长，用子代理当上下文防火墙"——**而检索在阶段二**。所以阶段一的子代理只剩"长任务拆分"和"可中止性"两类用途，看起来会有点大材小用。这不影响阶段一的价值（它验证的是机制能否接上闸），但要有预期。详见 [02-scope-v1.md](../02-scope-v1.md) 第二节末。

## 1. 总体形态

一句话：**Electron 桌面端（学生电脑）+ 一个轻服务端**。agent 内核以 SDK 方式内嵌 pi（跑在 Electron 主进程）；服务端只做知识库、检索、记录三件事，不感知 agent 内部结构。模型调用由学生自己的 API key 直连供应商，内容不经手服务端。

> **【阶段一】** 前半句成立（Electron 桌面端），**后半句整个不存在**——阶段一不联任何服务端。
> 阶段一的形态一句话就说完了：**一个 Electron 应用，里面装着一个 pi 内核。**

## 2. 端云边界与通道（对应端云图）【整节：阶段二】

三条 HTTP 通道，除此之外两端互不越界：

| # | 通道 | 方向 | 载荷 | 时机 |
|---|---|---|---|---|
| ① | 检索 | 本地 → 服务端 → 本地 | 问题 → 相关片段 + 出处（文件名 + 页码） | agent 答题需要资料时，同步 |
| ② | 激活 | 本地 → 服务端 | 邀请码 + 姓名学号 → 课程 token | 首次使用，一次性 |
| ③ | 记录上报 | 本地 → 服务端 | 提问 / 反馈 / 拦截事件 | 异步攒批，可关，学生可查 |

数据归属：

- **仅存本地**：会话 JSONL、项目代码、课程 token、权限配置、审计日志
- **仅存服务端**：课程知识库、标准答案与题库（不落学生盘）、使用记录
- **直连模型供应商**：学生提问内容 + 检索到的片段（学生自己的 key，服务端不可见）

边界原则：权限闸是本地端所有"出圈动作"的唯一通道；GUI 只经事件流读、经指令 API 写；工具层内只有检索工具知道服务端存在；服务端不感知多智能体结构。

> **【阶段一】** 本节只有两行是有效的：
>
> 1. **权限闸是本地端所有"出圈动作"的唯一通道**（"出圈"在阶段一指"动项目外的东西"）——这条阶段一就成立
> 2. **GUI 只经事件流读、经指令 API 写**——这条阶段一就成立
>
> 其余（三条通道、服务端数据归属）全部归阶段二。

## 3. 本地端结构（对应本地详图）

Electron 应用 = 渲染进程（GUI）+ 主进程（Node，承载以下全部模块），两进程之间走 IPC（事件下行推送 / 指令上行）。

### 3.1 GUI（渲染进程）四个视图

| 视图 | 内容 | 阶段 |
|---|---|---|
| **对话视图** | 消息流、流式渲染、**子代理过程树**、一键反馈 | 主体阶段一；出处卡片、反馈阶段二 |
| **会话中心** | 会话列表（空闲 / 运行中 / 待确认）、历史会话入口（pi -r 的界面化）、新建 / 切换、**切换不销毁** | **阶段一** |
| **权限中心** | 三档设置、确认弹窗（含子代理动作）、动作日志 | **阶段一** |
| **激活与设置** | 激活向导（邀请码 + 姓名学号）、告知同意（首次）、API key 配置、工作区信息 | API key / 工作区**阶段一**；激活向导、告知同意**阶段二** |

### 3.2 Agent 宿主（主进程，SDK 内嵌 pi）【阶段一】

- **实例池**：每会话一实例；懒创建（发出首条消息 / 打开历史会话时才建）；**切换会话不销毁**（后台任务继续跑，支持多会话并行布置任务）；运行中永不回收；空闲约 10 分钟 LRU 回收（时长可配置）。实例只是缓存，磁盘账本才是唯一事实——重建 = SessionManager 读 JSONL 重组上下文，秒级、无模型调用
- **会话装配器**：调 pi SessionManager 读 JSONL → 组装上下文 → 构造实例；同时是"历史会话入口"的数据源
- **事件总线**：把实例事件流推送给 GUI；steer / followUp / abort 接口是 GUI 指令的落点

**装配方式（v0.2 写实）**：

```
new DefaultResourceLoader({ cwd, agentDir, additionalExtensionPaths, extensionFactories, noExtensions })
      → await loader.reload()
      → createAgentSession({ resourceLoader })           // 扩展是"随 loader 一起给"的
      → await session.bindExtensions({ uiContext, mode: "rpc" })   // ← 漏了这步，闸形同不存在
```

⚠️ **三个必须记住的装配约束**（源码级结论）：

1. **每个会话一个独立 `ResourceLoader`**，但**共享一个 `ModelRuntime`**。共享 loader 会让会话 B 覆盖会话 A 的扩展 API 路由（`agent-session.ts:2580-2593`）。
2. **`bindExtensions()` 会触发 `session_start` 事件**，因此必须**在首条消息之前、且只调一次**。不调则扩展模式默认为 `print`，`ctx.hasUI === false`。
3. **不调用 `bindExtensions()` 的后果是静默的**：闸会按"无 UI 则拒绝"处理，表现为"agent 什么都不肯干，且不报错"。

### 3.3 子代理【阶段一：通用基座；资料检索子代理：阶段二】

**v0.2 改写**：不再是"独立 pi 进程"，而是**复用 `pi-subagents`（nicobailon）**，采用它的**混合进程模型**。

| 任务类型 | 进程模型 | 理由 |
|---|---|---|
| 前台、短任务 | **父进程内的独立 `AgentSession`**（不是新进程） | 闸天然可达，启动零成本 |
| 后台、长任务、不受信任务 | **detached runner 独立进程** | 跑飞了拖不垮主应用，**可以真杀**（Windows `taskkill /T /F`） |

> 依据（包自己的源码原文）：*"A child is a pi `AgentSession` created **inside the process that owns it**: the parent pi process for foreground children, the detached runner process for background children."*

**我们仍然要自己写的部分**（复用 ≠ 零工作量）：

| 项 | 说明 |
|---|---|
| **子代理定义文件** | 通用基座（阶段一）、资料检索子代理（阶段二）——内容由我们写 |
| **`task` 工具的接入** | 让主 agent 知道"什么时候该派子代理"：系统提示词 + agent 描述 |
| **调度参数** | 并发上限 / 超时 / 嵌套深度。起步值：**全局 4 / 单父 3 / 深度 1** |
| **超时机制** | 生态普遍缺失，必须自研（参考 gotgenes 的 `forwardingTimeoutMs` + 2 秒 grace） |
| **GUI 过程树** | 包有生命周期事件，但**没有任何现成的"子代理过程树"UI**（OpenClaw 也没有）——可能是产品差异点 |
| **审批弹窗的归属标注** | "是哪个子代理发来的请求"——包与 OpenClaw 都未覆盖 |
| **堵 `pi -p` 绕过洞** | 见下 |

⚠️ **需求 5 的未闭合缺口（本架构最大风险）**：`pi-subagents` 的权限能力与我们"主/子共用同一道闸"有已知偏差——**bash 策略它明确不管**（`src/runs/shared/permissions.ts:20`：*"pi-subagents leaves bash policy to pi-guard"*），**前台进程内子会话的 `ask` 不转发到父 UI**。补法是靠 `@gotgenes/pi-permission-system` 的转发通道，但**必须实测**。详见 [ADR-0006](./adr/0006-subagent-process-model.md)。

⚠️ **`pi -p` 绕过洞**：子代理只要用 bash 跑一句 `pi -p "..."`，就起了一个**全新的、没有任何闸的进程**。必须在权限规则里把"通过 bash 启动 agent 进程"列为黑名单。用例见 [test/permission-cases.md](../test/permission-cases.md) PC-C-11。

### 3.4 权限闸【阶段一】（**本阶段核心复杂度**）

**v0.2 改写**：挂点定在**扩展层**（`pi.on("tool_call")`），实现上**复用 `@gotgenes/pi-permission-system`**；审批请求经**我们自己的 `ApprovalService`** 排队后弹给 GUI。

流水线：**拦截点（扩展 `tool_call`）→ 白名单**（项目目录内常规读写、常见安全命令 → 放行）**→ 黑名单**（大面积删除、出项目目录、联网、全局安装 → 弹确认）**→ 灰区判官**（小 agent 评危险系数；拿不准 = 危险；学生的问题、代码输出属不可信内容，不得影响判断）**→ 三档执行**（变更前确认[默认] / 自动审批 / YOLO）**→ 审计日志**（全部动作落盘可查）。

档位决定"要不要先问"，不决定"要不要告诉你"。

**我们负责的部分**（包不提供）：

1. `ExtensionUIContext` 的 Electron 实现（TUI / RPC 之外的**第三**份实现）——可照 `src/modes/rpc/rpc-mode.ts:136-208` 的形状
2. **三档用户界面**（没有任何候选包提供）
3. 灰区判官的 authorizer link 挂载（⚠️ `pi-permission-ai-guard` 与当前主包**版本不兼容**）
4. **启动自检**：扩展加载失败是**静默**的（只进 `errors[]`），必须自己检查"闸到底装上没有"，否则拒绝启动
5. **供应链锁定**：锁精确版本（该包迭代极快）
6. **审批排队（arbiter）**：pi **不做任何 UI 序列化**，主/子同时弹窗会互相覆盖（官方 issue #7007 有实证）→ 必须自己串行化

⚠️ **已知代价（accepted cost）**：这是**扩展层**方案，`event.input` 可变且**改后不重新校验**，因此**它不是防篡改的安全边界**。这个代价是选择"复用社区扩展"换来的，已在 ADR-0007 中记录并接受。

**fail-closed 三处**：`ctx.hasUI === false` → 拒绝；handler 抛异常 → pi 拒掉工具；审批超时 / GUI 崩溃 → 按拒绝处理。

## 4. 服务端结构（简）【整节：阶段二】

四个服务 + 一个存储：**接入**（邀请码、学生登记、token 签发）、**知识库**（上传、解析/切分/索引，保留出处元数据）、**检索**（问题 → 片段 + 出处；标准答案与题库不在此通道返回；向量 + FTS5 混合检索）、**记录**（事件存档、期末导出）；存储用 SQLite 单库（sqlite-vec 向量索引 + FTS5 关键词索引）。部署在自己租用的云主机。
