# ADR-0004：RAG 采用混合检索

- 状态：**已接受**
- 日期：2026-09-14
- 决策人：项目组
- 相关：[ADR-0003](./0003-server-on-rented-vm.md)、[ADR-0005](./0005-retrieval-tool-extension.md)

## 背景

服务端要把老师上传的教材（PDF）和课件（PPT）做成可检索的知识库，并且**每一条检索结果都必须带得出出处**（文件名 + 页码），因为需求要求"回答有出处，且出处只从检索片段里引用"。

纯向量检索和纯关键词检索各有短板：向量检索抓语义但会漏掉精确的术语/代码符号；关键词检索抓精确匹配但不理解同义表述。

## 决策

**混合检索**：

- **向量通道**：商用 embedding API 生成向量，`sqlite-vec` 存索引
- **关键词通道**：SQLite FTS5
- **两路结果合并去重**

分块原则：

- 按页 / 按段切分
- 每块带出处元数据（文件名 + 页码）
- **代码块整块不切碎**

embedding 属服务端职责，费用由服务端承担（单班量级可忽略）。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
|---|---|---|---|
| **混合检索**（选中） | 语义 + 精确双保险；出处元数据可控 | 两套索引要维护；合并去重需要调参 | — |
| 纯向量检索 | 实现简单 | 代码符号、公式、专有名词容易漏 | 课程资料里代码和公式占比高 |
| 纯 FTS5 | 零成本、无外部依赖 | 学生问"为什么报这个错"这类语义问题基本搜不到 | 教学场景的核心用法会失效 |
| 自建 embedding 模型 | 无 API 成本、数据不出境 | 部署重（GPU 或 CPU 推理都很慢）；效果通常不如商用 API | 单班量级省不下钱，反而增加运维 |

## 后果

### 正面
- 出处质量高：分块时就绑定页码，不依赖模型自己编
- 单机 SQLite 就能支撑（见 ADR-0003）

### 负面 / 代价
- **embedding API 是外部依赖**：服务端要能出网；供应商变更会影响到索引（换模型要重建全部向量）
- 上传资料后要等解析 + 建索引，老师端需要"处理状态可见"
- 合并去重的策略需要调（分数不可比：向量相似度和 BM25 分数不是一个量纲）

### 需要后续跟进的事
- [ ] 定 embedding 供应商与模型，并**记录在案**（换模型 = 重建索引）
- [ ] 分数融合策略（RRF？加权？）与 top-k 参数，写进 [server-api.md](../server-api.md)
- [ ] 解析失败的错误分类与提示（PPT 解析是最容易出问题的一环）
- [ ] 代码块切分规则的具体实现

## 什么情况下该重新审视

- 如果试点发现检索质量不够（见需求第 5 节：第一版知识库只有教材和课件，回答质量有上限）
- 如果 embedding 供应商涨价或条款变化
