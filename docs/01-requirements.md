# 课程 Agent 助教 · 需求文档

- 版本：v1.0.1｜日期：2026-09-14｜状态：试点决策已定（见第 6 节），待老师评审
- 本文档替代 v0.1 / v0.2。那两版把产品定位写成了"网页答疑客服"，与实际方向不符，已废弃。
- 2026-09-14 修订：本地端形态定为 Electron 桌面应用（渲染进程 GUI + 主进程 Agent 宿主），pi 以 SDK 内嵌；安装方式由 npm 调整为安装包（见决策 5/6）。

## 1 这是个什么产品

一句话：**给编程课学生的本地 AI 助教**——像一个装在学生电脑上的 coding agent，能直接读他的代码、跑他的代码、把问题修好；解释问题的时候，引用课程资料（教材、课件）作为依据。

画面是这样的：学生晚上写实验作业卡住了，编译报错看不懂。他打开我们的界面，就像打开其他有图形界面的 agent 产品一样，贴上报错，或者直接说"帮我看看为什么跑不起来"。agent 读他的项目文件，自己跑一遍，复现出这个报错，找到原因，一边动手一边解释，解释里注明"课件第 X 章 / 教材第 Y 页是这么说的"。最后代码改好（改之前学生会确认），跑通了。

和"微信群问老师"的本质区别：老师只能看你贴过去的截图，agent 是真的在你电脑上把问题修了。

**学生和老师不是两套系统。** 工具只有一套，区别只在数据权限：老师持有标准答案和官方知识库（可写），学生拿到课程知识库（只读）和自己的项目。权限挂在数据上，不挂在角色上。

## 2 第一版做什么

第一版只做学生工作区，目标很朴素：一个班的学生能真的拿它来问问题、调作业。

agent 有三个工具：

| 工具 | 来源 | 作用 |
|---|---|---|
| 检索课程资料 | 自研（第一版唯一的新工具） | 把问题发给服务端，拿回带出处的资料片段 |
| 读写项目文件 | pi 自带 | 直接看学生的作业代码 |
| 执行命令 | pi 自带 | 复现报错、验证修改、跑测试 |

**多智能体第一版就上**，机制直接用 pi 自带的 subagent 扩展：每个 subagent 是一个独立的 pi 进程、有自己隔离的上下文，定义一个新 agent 就是写一个 markdown 文件。第一版的分工：

- **主 agent**：接待学生、调度 subagent、面对学生
- **通用 subagent**（基座）：能力完整，负责长时、复杂的任务——主 agent 觉得活太大时，拆成几块派出去，干完只汇报结果
- **资料检索 subagent**：通用基座加两条限制（只给课程检索工具、只读）。单独留它有个实际原因：检索返回的资料片段可能很长，直接进主 agent 上下文容易撑爆——让它在自己的上下文里消化，只回给主 agent 一份带出处的摘要

专用 subagent 都这么做：**通用是基座，专用 = 通用 + 工具限制 + 提示词聚焦**。第二阶段的批改、备课，就是再加几个这样的 markdown 文件。

一条原则：**改学生文件、跑命令，不管是主 agent 还是 subagent 干的，都走同一道权限闸**（分档见下）；subagent 的动作在界面上和主 agent 一样可见、可中止。

**权限分三档**，学生在设置里随时切换，决定权限闸有多严：

| 档位 | 行为 | 适合场景 |
|---|---|---|
| 变更前确认（默认） | 每个改动动作都弹确认，点了才执行 | 第一次使用、改重要作业 |
| 自动审批 | 危险系数低的动作自动放行，高的通知学生手动确认 | 日常使用 |
| 完全访问（YOLO） | 全部放行，不再询问；开启时有醒目警告 | 大批量、重复性任务 |

只读动作（读文件、检索资料）任何档位都不拦。

自动审批档判断危险的办法：先过项目组预置的黑白名单——项目目录内的常规读写、常见安全命令直接放行；删大面积文件、动项目外的东西、联网、装全局包之类直接拦下问学生。名单覆盖不了的灰区，交给一个小 agent 判断危险系数：它只干这一件事，拿不准就当危险处理。学生的问题、代码输出都属于不可信内容，不能影响危险判断。

界面上的基本要求：

- **安装**：Electron 桌面应用安装包，双击即用（自带运行时，学生电脑无需预装 Node.js）
- **课程激活**：输入课程邀请码，登记姓名学号（只用于老师认人，不做账号密码体系），拿到本课程的"课程工作区"
- **模型配置**：学生在设置里填自己的大模型 API key，调用费用自理（pi-ai 支持的供应商都能用）
- **干活过程实时可见**：agent 在读哪个文件、跑什么命令，学生看得见，和用其他 coding agent 一样
- **改动要过权限闸**：按学生选的档位走，见上文"权限分三档"
- **回答有出处**：解释用到课程资料时注明出处。出处只从检索工具返回的片段里引用，不让模型凭空报页码；资料里没有的，明说"资料里没有，以下是我的理解"。试点中若引用频繁出错，再加一个核对 agent——多智能体结构下就是加一个 markdown 文件的事
- **能反馈**：觉得回答不对劲可以一键反馈，记录到服务端

第一版明确不做：

- **作业批改 / 练习模式**：背后需要一整套标准答案管理方案（答案只许在服务端、怎么防泄漏），放第二阶段。无论哪个版本，系统都不替老师打分
- **老师工作区**（教案 / PPT 制作 / 批改发布）：第二阶段，在同一个内核上加工具
- **转老师队列**：老师端还不存在，问题没解决先走线下
- **学情分析**：第一版只收集记录，不做任何分析

## 3 系统长什么样

本地端（学生电脑）+ 一个服务端。

```
      学生电脑                        服务端
┌──────────────────┐             ┌────────────────────────┐
│ Electron 应用    │   检索请求   │ 课程知识库（老师管理）   │
│ · 资料检索工具    │ ──────────▶ │ 检索接口                │
│ · 文件读写 / 命令 │ ◀────────── │ 使用记录收集            │
└──────────────────┘ 资料片段+出处 └────────────────────────┘
```

课程资料检索放在服务端，而不是把整个知识库同步到学生电脑，理由有三：

1. 题库、标准答案只存在服务端，学生本地翻遍磁盘也找不到，防泄漏
2. 老师更新资料立刻生效，不存在"张三的库是上周的版本"
3. 学生端零维护，装上就能用

服务端就三件事：

- **知识库管理**：老师上传教材、课件（PPT / PDF / Markdown），自动解析建索引，处理状态可见
- **检索接口**：接收问题，返回相关资料片段和出处
- **记录收集**：学生的提问和反馈存档，给以后的学情分析攒原料

关于多智能体：编排在第一版就通过 pi 的 subagent 扩展实现（见第 2 节）。本地端 agent 的数量对服务端是透明的——服务端只认检索请求和记录上报，不关心主 agent 委派了几个 subagent。

## 4 硬规矩（不讨论，必须满足）

1. 不替老师打分。评分永远是人的事。
2. 学生的提问内容会发送给商业大模型 API。学生第一次使用时必须明确告知并取得同意，告知文案经老师过目。
3. 发给大模型的请求里不带学号、姓名；学生之间看不到彼此的提问；模型供应商由学生自己选，项目组推荐数据条款友好的（可关闭训练用途的），选择权和责任都在学生。
4. 标准答案、题库只存服务端，不落学生磁盘。
5. agent 对学生机器的每个动作在界面上全部可见、可追溯，绝不隐瞒执行。权限档位决定"要不要先问"，不决定"要不要告诉你"。
6. 服务端收集学生的记录必须透明：记了什么，学生自己能看到。

## 5 怎么算第一版成功了

试点一段时间（时长和老师商定，建议 4–6 周），看三件事：

1. 有多少学生真的在用（每周活跃人数）
2. 学生的反馈里"解决了问题"占多大比例
3. 学生是否还在继续用（周留存）

具体数字目标在试点开始前和老师一起定，定了写进这一节。另外要有预期：第一版知识库里只有教材和课件，回答质量有上限——试点本身就是摸清还缺什么资料（见第 6 节第 4 条决策）。

## 6 试点决策（已定）

| # | 问题 | 决定 |
|---|---|---|
| 1 | 模型调用走谁的 key，谁出钱？ | 学生在本地配置自己的 API key，自己掏钱；服务端不做模型网关 |
| 2 | 试点用哪门课？ | 人工智能课程 |
| 3 | 学生数据发商业大模型 API 有没有合规规定？ | 没有。这是实验性作品，不保证投入学校实际使用；首次使用的告知同意保留，文案从简 |
| 4 | 知识库要不要补实验指导书、历年 FAQ？ | 暂时不补，第一版只用教材和课件；回答质量上限受此限制，试点中再评估 |
| 5 | 学生端怎么装到电脑上？ | Electron 桌面应用安装包（自带运行时，学生电脑无需预装 Node.js） |
| 6 | 本地端技术形态与 pi 集成？ | Electron 桌面应用；pi-agent-core 以 SDK 内嵌主进程 |
